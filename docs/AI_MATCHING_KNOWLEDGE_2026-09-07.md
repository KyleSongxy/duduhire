# AI 人才与企业出海：发现和匹配知识库

资料核对日期：2026-09-07。知识版本：`2026-09-07.1`；示例版本：`2026-09-07.2`。

本次把行业知识用于帮助提问、识别可编辑的工作条件和解释匹配结果。知识条目不能证明某个人具备能力，也不代替用户对自己的资料进行确认。

以上为方法概括和本产品的实施选择，未抓取第三方个人档案、联系方式或付费内容。所有示例均另行编写。

## 可维护结构

- `apps/api/src/domainKnowledge.ts`：官方来源、核对日期、七类场景、双向提问、字段提示、核实方向、技能同义表达。
- `apps/api/src/naturalMatchingConditions.ts`：按双方不同含义，识别自然语言中的合作方式、目标市场、工作语言、预算、开始日期和每周投入。
- `apps/api/src/matching.ts`：从已确认字段生成可编辑建议；校验公开内容；执行硬条件排除、明确缺口和后续核实问题。
- `apps/api/src/matchingExamples.ts`：22 条虚构需求和人才资料，以十一个业务场景成对覆盖。
- `apps/api/migrations/008_matching_knowledge_and_examples.sql`：扩展技能词表、可选合作条件和独立示例表。

知识检索使用可审查的场景词和有限条目，每次最多提供三条。模型只能把它们用作理解场景和寻找缺口的参考，不能把知识条目的内容写成用户事实。没有合适领域时回到“场景—工作—行动—结果”的通用方法。

## 场景提问与交付核实

| 场景 | 需求方先说明 | 人才方先说明 | 推荐后的核实材料 |
| --- | --- | --- | --- |
| 企业知识库和 RAG 问答 | 用户最常问的问题、资料现状、先试用还是接入系统 | 本人做了文档处理、检索、回答、评估中的哪些部分 | 引用示例、失败样本、试点与正式使用范围 |
| AI 助手与自动化 | 当前最费时的一步、输入输出、必须人工确认的动作 | 接通的系统、自动步骤、失败与权限处理 | 流程说明、测试用例、人工接管与运行记录 |
| 模型评估和提示词改进 | 任务、不能接受的错误、现有样本 | 对比方法、样本来源、本人改动 | 样本集、指标定义、复现记录与错误分析 |
| 目标市场与进入策略 | 产品、客户、国家或地区、当前阶段 | 哪个市场和行业、本人负责哪一步 | 来源表、客户研究、访谈记录和阶段建议 |
| 海外获客与增长 | 已有渠道、目标客户、首阶段结果 | 内容、投放、网站或转化分析中的本人工作 | 渠道记录、投入口径、线索与订单的分别统计 |
| 内容本地化和海外支持 | 目标用户、工作语言、内容范围与覆盖时段 | 具体文稿、语言工作用途与编辑职责 | 术语表、稿件、审校记录和支持流程 |
| 渠道伙伴与跨境协同 | 产品、市场、合作方类型和所需业务环节 | 伙伴研究、谈判、订单或交付协调职责 | 筛选依据、沟通记录、交付计划及专业机构责任边界 |

这里的提问是按缺口选用的提示，不要求用户依次填写整套问卷。已明确的信息不再重复追问；材料暂缺时继续整理可确认的部分。

## 精准解析的边界

1. 匹配建议只来自当前已确认发现记录中 `provided` 字段的证据引用：`user:<requestId>` 必须在对应原始用户消息中逐字找到，`attachment:<requestId>` 必须在对应材料文本中逐字找到。技能、领域判断、合作条件与公开摘要均使用这些已定位引用，旧版 AI 扩写的字段 `value` 不参与。错误来源、AI 回复及缺失原文不作为依据，也不改动已确认的历史存储。
2. 人才技能优先读取“本人职责”和“具体行动”；团队背景和结果不能自动变成个人技能。
3. “不会 RAG”“没有做模型微调和前端开发”“广告投放由同事负责”“想学习模型部署”不形成对应能力标签。
4. “用过 AI”不自动补齐模型训练、RAG、评估等能力；出现 Shopify 作为内容发布平台也不自动等于跨境电商运营。
   同时支持有限的“场景＋本人动作”归类：海外背景中的市场调研归为海外市场调研，明确开发 B2B 线索归为海外获客；AI 工作流中的 CRM 接入归为系统集成。工作技能仍须有行动原句，单独出现市场名或平台名不成立。
5. 远程、项目合作、每周投入等建议保留原句依据。现场办公需要填写城市；不从客户地址或过去工作的城市推断工作地点。
6. 工作语言来自明确的沟通、撰写或翻译用途。国籍、出生地、留学和旅游经历不参与推断。“德语加分”不成为必须具备的语言条件。
7. 预算只有金额、币种和计价周期明确时才可比较。模糊的“几万”“可商议”保持空缺；不自动换汇。
8. 建议仍然可以编辑和删除；确认发现内容不会自动发布匹配资料。

公开预览和发布校验会提示常见联系方式、链接和敏感文本。它不是完整匿名化服务，因此公开简介始终保留给用户检查的机会。

## 双向匹配规则

候选首先必须属于另一侧、具有共同的工作能力，且需求方明确设为“必须具备”的技能已在人才公开资料中列出。明确冲突的办公方式、合作方式和现场城市不会通过排名弥补。

可选条件的含义固定如下：

| 条件 | 需求方含义 | 人才方含义 | 自动判断 |
| --- | --- | --- | --- |
| 市场 | 工作必须覆盖的市场经验 | 本人填写的服务或项目市场 | 常见中英文别名规范化后逐项核对；不以部分字符串或相邻国家代替 |
| 工作语言 | 工作必须使用的语言 | 本人填写的可用工作语言 | 必须全部覆盖；加分项保留在说明里 |
| 金额范围 | 预算范围 | 报价或期望报酬范围 | 币种、计价周期相同时排除明显不相容区间 |
| 每周投入 | 最低所需小时数 | 最多可投入小时数 | 供给低于需求时排除 |
| 开始日期 | 最晚可接受开始日期 | 最早可开始日期 | 人才可开始时间晚于需求日期时排除 |

条件缺失时，结果显示“待确认”并指出具体缺口，不把空值当作满足条件。市场和语言有明确填写但未覆盖需求时不展示该条；未填写时保留为待核实结果。自由文本补充条件继续显示供双方检查，不声称已自动理解全部条款。

排序目前依共同已确认技能数量、明确相容条件数量、稳定记录标识进行。它不使用姓名、年龄、性别、国籍、学校、受欢迎程度或自由文本关键词来加分。输出包括共同技能、尚未列明能力、相容理由、待核实事项和可直接使用的追问，不输出成功率或“匹配百分比”。

“条件相容”只表示所填字段的比较结果，不表示能力通过独立验证。经历和资料始终注明本人自述；具体作品与贡献仍需双方核实。

## 示例资料与真实记录隔离

22 条示例覆盖：知识问答、自动化助手、模型评估、数据与模型服务、新加坡 B2B 研究、美国独立站增长、日本内容本地化、德国渠道伙伴，以及德国 B2B 兼职、美国英语内容项目、n8n 兼职协作。

示例存于独立的 `matching_examples` 表，没有用户、联系人、发现会话或发布身份。列表标题、简介与结果说明都标识虚构示例；API 返回 `isExample: true`、`contactable: false`。真实候选查询只读 `matching_listings`，不会从示例表回填人数或推荐结果。

私密预览 `POST /api/v1/me/matching/preview` 只读取示例库，要求用户已确认发现内容，仍可调整待发布草稿。它不创建发布记录；示例库为空时明确返回未导入状态，不静默创建示例。真实匹配继续要求单独确认公开资料和发布授权。

本地开发导入步骤（先在进程中配置开发数据库环境变量）：

```sh
npm run db:migrate
npm run db:seed:matching
```

导入命令只允许本机数据库，按固定示例标识更新；重复导入不新增重复记录，不修改用户表或真实发布表。运行时数据库角色只有示例表的读取权限。

## 回归与后续维护

`apps/api/test/matching.test.ts` 覆盖技能否定、本人归属、原句建议、自然条件、预算维度、投入方向、日期、地区语言别名、明确冲突、缺失信息、可解释结果和示例成对覆盖。`matchingProviderFixtures.ts` 保存八条合成场景的真实 Qwen 初稿措辞，回归检查其技能预填与示例可匹配性。`apps/api/test/auth.test.ts` 覆盖未登录和未确认拦截、私密预览不发布、示例与真人隔离、空示例库状态及真实匹配的发布流程。自然条件提取另有独立回归用例；PostgreSQL 集成用例增加了合作条件持久化和示例只读权限检查。

新增知识时同时更新：来源和核对日期、领域条目、技能词表与数据库约束、正反解析样本及匹配回归。新增技能必须代表可交付的工作能力，不能只有工具名和流行概念。新增示例必须继续保持虚构标识、无联系方式、独立存储和可重复导入。

当前是经人工整理的小型版本化知识库。它有明确来源和可检验规则，但不等同于全行业知识覆盖、持续自动更新的政策库、第三方人才认证、项目成交保证或语义匹配准确率验证。
