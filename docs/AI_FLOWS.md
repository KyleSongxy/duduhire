# 两端 AI 交互与确认流程

更新日期：2026-09-07。沿用原有页面布局、输入框、对话区域与能力卡的视觉设计，在原区域增加快捷操作、可核对的字段和匹配条件。流程提示版本为 `duduhire.discovery.v2.1`；JSON 契约仍为 `flow.schemaVersion: 2`，不是新的 schema 2.1。

## 1. 流程与完成标准

| 入口 | 收集字段（按缺失情况追问，非固定轮数） | 必要事实 |
|---|---|---|
| 梳理用人需求 `/talent` | 工作背景 context、主要工作 work、预期结果 outcome、合作方式 collaboration、时间与合作条件 constraints、必要能力与加分经验 requirements、面谈核实重点 verification | context / work / outcome |
| 完善能力档案 `/projects` | 经历背景 situation、个人职责 role、具体行动 actions、实际结果 outcome、可提供的依据 evidence、适合承担的工作 direction、合作偏好 preferences | situation / role / actions / outcome |

状态：`collecting → ready → confirmed`；修改已确认事实回到待确认状态。模型负责理解、字段归类、选择证据和提问，状态转换由服务端确定。必要事实必须来自用户或附件，AI 推断与跳过不能满足必要事实。结果可以是定性变化，不强制数字；材料、预算和偏好可稍后补充。所有字段都可以暂跳过，但缺少必要事实的草稿不能标记完成。

一次读取完整段落、JD、项目经历和附件，同时提取其中已经说清的多个字段。必要事实齐全后立即进入 `ready`，展示可编辑草稿，不必逐项回答全部可选问题或先点击生成草稿。必要事实未齐时只追问一个最有价值的缺口；模型给出的重复问题、无对应字段的问题或抢在必要信息前的可选问题，会由服务端替换。

岗位明确的 HR 不需重走业务诊断，OPC 不默认全职招聘；个人能力不把团队成绩当个人成绩。草稿沿用原对话和能力卡，补充字段状态及可展开的来源摘录。AI 人才与企业出海使用有来源的场景提示辅助理解，涵盖知识问答、自动化、评估、市场进入、增长、本地化和渠道协同；知识提示不成为用户事实或默认招聘要求。具体结构和来源见 [领域知识库](AI_MATCHING_KNOWLEDGE_2026-09-07.md)。

## 2. 快捷入口与输入框操作

页面中的场景示例只填入输入框，不自动提交。用户可以参考一段完整需求或经历的写法，改成实际情况再发送；仍含 `【示例输入，请替换为真实情况】` 等明确示例标记时，前后端都会阻止把它收集为真实事实。原有草稿保留，不把示例确认为个人经历。

- `先生成草稿` / `查看草稿`：展示已知字段与空缺。必要信息齐全才进入 ready。查看已确认版本不会撤销确认。
- `暂时跳过`：当前尚未回答的字段记为稍后补充，保留已知信息；也支持“这个先不填”“还没想好”等简短表达。能力流程中的“没有材料”只将依据留待补充，不会误跳过本人职责。
- `继续完善`：优先补必要缺口；必要信息齐全后，可主动继续补可选条件。随时查看草稿即可退出可选追问，也可直接输入纠正意见。
- `确认保存当前版本`：只有 ready 且必要事实齐全，并且会话版本与用户所见相同时确认；模型不能代替用户确认。
- 自然语言修改，例如“我只是参与开发，不是负责人”：更新事实、清除旧结论，重新邀请确认。
- `新对话`：沿用原按钮与确认交互，将原会话归档，保留既有数据直到保留期清理。

快捷按钮使用同一套命令和版本校验，不另设绕过确认的路径。输入框已有未发送内容或附件时，不会把它们悄悄合并进一次快捷确认。“好”“确认”或引用确认命令的问句不触发保存确认。含附带修改的确认句交给模型解释和更新，不能同时确认未读的新内容。

## 3. 来源与信任

`fields` 中每项包含文本、`provided/inferred/skipped` 状态和 `{sourceId,quote}`。来源 ID 使用 `user:<requestId>` / `attachment:<requestId>`，跨轮保持稳定。`provided.value` 由服务端使用有效引用的原句生成，保留否定、本人/团队归属、预计与已实现等限定词；模型扩写的工具、职责、交付保证和硬条件不会直接写成事实。数值照录原文，例如“二十四小时”不会因模型改写为 `24` 而使有效引用整轮失败。建议标题中的数字按完整指标核对，无据或过长标题直接省略，不把 `n8n`、`B2B` 等标识符里的数字误作业绩。

引用必须逐字存在于对应的用户或附件来源。模型将不相邻的句子合并成一条引用时，只有每个完整片段都逐字存在于同一来源才拆成独立证据；不做模糊匹配。历史 AI 回答不能作为事实依据。旧附件不能覆盖较新的用户纠正。

需求的工作正文、能力的价值正文取自已接受字段，模型扩写的 `provided.value` 和 `summary.value` 会被丢弃，不因这些未使用文本的数字改写或长度拒绝有效原句。模型提炼的标题明确标为“AI 建议方向”；`inferred` 内容始终是待确认建议，不能满足必要事实，也不用于自动提取已具备技能。没有真实来源或引用不存在时仍然拒绝，不接受编造证据。

这只是来源追溯和结构校验，不是独立事实核查。引用存在不证明陈述真实，模型仍需真实样本评测和人工核对。“用户已确认”仅代表认可表述，不能显示成平台认证。确认不会自动公开档案或需求；参与匹配需要下面单独的预览与发布同意。系统不自动联系候选人或作出雇佣决定。

## 4. 接口、恢复和保密

模型使用 Qwen 官方接口；服务端密钥、模型和地域配置见 [部署指南](DEPLOYMENT.md#qwen-api-接入)。客户端不持有密钥。无密钥拒绝启用 Qwen；超时、限额、错误或无效 JSON 不返回伪造本地回答，且不会写入半成品。

对话与草稿存 PostgreSQL；去掉旧 8 轮上限，仍保留请求限速与输入/上下文预算。模型最多读取 48,000 字符的近期来源，并带入已有字段和引用；更旧的原始材料仍保留在数据库，但不保证每轮全文进入模型。

前端传 `expectedThreadId` 和 `expectedVersion`，保存前后都进行并发校验；已保存请求按 requestId 幂等。冲突后读取最新状态、保留用户输入，不自动确认新版本。输入文本短时缓存于当前浏览器会话，按账户和原 mode/入口隔离；切回原身份时可恢复其文字，不将文字带入另一流程。附件正文不放浏览器缓存，刷新或离开页面前尚未提交的附件需重新添加。sessionStorage 不可用时当前编辑仍可使用，但不保证刷新或切换后的恢复。

浏览器仅支持文本附件摘录：每个前 8,000 字符、最多 5 个，服务端合并本轮材料最多 12,000 字符。无原文件托管、PDF/Word 解析、病毒扫描或外部链接抓取；建议先脱敏，不提交与目的无关的个人信息。

## 5. 确认之后：双向匹配

原发现流程继续使用 Qwen。匹配采用 `evidence-skills-v2` 确定性规则，不再调用模型，也不让模型生成候选人 ID、项目 ID、录用建议或“匹配置信度”。确认草稿后，用户可以先私密比较独立示例；真实匹配只比较本站用户明确发布且仍有效的资料。

### 条件预填与私密示例

系统从当前已确认的 `provided` 字段预填标题、摘要、技能和能明确识别的合作条件，并返回建议所依据的原句。人才技能只从本人职责和具体行动提取，背景中的团队工作、否定、尚在学习的技能不会自动计入。用户可以修改或删除任何建议，不必重新抄写整份需求或档案。

自然语言可提取远程、项目/兼职/全职、明确目标市场、实际工作语言、金额与币种/计价周期、每周投入、明确开始日期。现场城市由用户填写，不根据过去项目所在地推断住所或到场能力。模糊预算、未知日期、语言加分项和相互矛盾的条件保持待核对；不自动换汇。更多条件在原匹配区域中展开填写。

“查看示例匹配”不要求勾选公开同意，也不创建发布记录。示例读取独立 `matching_examples` 表；开发 seed 定义 22 条（11 条需求与 11 条人才），实际数量由导入批次决定，不能把 seed 数量视为部署数据库总数。当前用户仅比较对侧示例，按 ID 最多读取 100 条。它们无真实账户、联系人或发布身份，返回 `isExample=true`、`contactable=false`，不能联系或发起合作。示例也执行相同硬条件，不为展示结果放宽要求。未导入示例库和有示例但无符合项分别返回明确状态；真实结果不会混入示例填充人数。

### 发布与退出

1. 完成并确认所见需求或能力档案后，使用原页面内的“查找合适的人才”或“查找合适的项目”。未确认时先继续原对话。
2. 阅读“匹配资料预览”：自行核对标题、摘要、工作标签、合作方式、工作方式、地点与补充说明。建议内容可以修改，不能把 AI 提炼当作发布同意。
3. 核对从 34 个受控标签中预选的 1–8 项，可增删；需求方可将已选标签中的部分设为必须具备，人才不能设置对方的必需技能。现场或混合办公必须填写地点。市场、语言、预算、投入和日期为可选条件，有明确填写时按下述语义参与比较。
4. 发布同意框默认不勾选。匹配预览的文字与来源线程/发布版本可按当前浏览器登录会话和类型短期恢复，但 consent 不保存、不恢复，必须重新检查并勾选。恢复草稿的来源或发布版本过期时仍阻止发布，不能用恢复操作绕过版本核对。明确勾选并提交后，以上预览字段才成为可向其他已登录用户展示的匹配资料。个人资料、原始对话、附件、引用、邮箱和联系方式不会自动公开；预览中也不要自行填写个人联系方式或机密。
5. 发布后可在同一区域刷新结果、修改展示资料或“退出匹配”。更新也需确认预览及同意；退出会使后续服务端查询不再返回这份资料，但无法撤销他人已经阅读或保存的内容。

每个账户同一类型最多保留一份发布记录。发布快照绑定当时活跃对话及其版本；继续发送对话消息、修改或新建对话后，旧发布不再参与匹配。即使普通问答没有改变已确认事实，只要保存了新对话版本，也需要重新预览并发布；这是当前保守的版本保护，不应误报成平台审核失败。单纯刷新页面不改变版本。

“退出匹配”只是撤回可见性，不会删除账户、发现记录或历史发布数据。归档发现线程按已有保留期清理时，其关联匹配记录随外键级联删除；尚未归档的撤回记录没有独立自动删除期限。

### 结果是什么意思

- 需求方只看能力资料，人才只看需求项目；不匹配本人、同类型、未发布、已撤回、来源过期或未确认的记录。
- 至少有一项共同工作标签才可能出现；项目设定的必需标签缺失时不返回。明确不兼容的合作/办公条件会排除，而“可协商”不当作已经达成一致。
- 双方都明确要求现场或混合办公时，城市不同会排除；如果一方办公方式可协商但填报城市不同，则保留为待确认的到场安排，不默认接受异地合作。
- 需求方填写的市场经验与工作语言是工作必须覆盖的条件；人才填写的是本人声明的覆盖范围。双方明确填写但未全部覆盖时排除；人才未填写时显示缺口，不认作已满足。常见中英文名称按明确别名规范化，不用部分字符串或相邻国家替代。
- 同币种、同计价周期的预算/报酬区间明确不相容时排除；条件不足时保留待确认。人才每周最多投入低于需求最低投入，或最早可开始日期晚于需求最晚可接受日期，也会排除。
- 结果展示共同标签、相容理由、尚未列明技能、条件缺口，以及最多三个可继续核实的问题。排序依据共同标签数、明确相容条件数与稳定记录标识，不使用姓名、年龄、性别、国籍或学校加分。
- `conditions_aligned` 仅表示所填条件相容；`needs_confirmation` 表示仍有条件缺口。两者都不代表能力通过验证、面试结果或录用决定，作品和本人贡献仍需核实。
- 当前最多在一批 500 份有效资料中比较，最多返回 20 条；`catalogLimited=true` 表示查询范围受限，不代表已搜索所有资料。补充说明只作展示，未自动理解全部条款。
- 没有符合条件的真实发布记录时，明确显示空结果，不生成示例人才或项目填充。当前不能在站内联系、发消息、保存短名单、签约或付款。

发布、撤回和结果接口见 [API 契约](API.md#双向匹配)。匹配词表与规则由服务端统一维护，前端不能提交任意技能名或供应商生成的候选人标识。

## 6. 验证边界

单测覆盖两端一次多字段采集、必要齐全早成稿、可选跳过/继续、来源引用与扩写防护、确认、修改再确认、示例标记拦截、供应商失败和旧数据兼容；API/数据库测试覆盖版本、幂等、重置归档、旧附件和超过 8 轮。隔离浏览器测试用显式 local 演练模式，不消耗真实 API。本地演练支持原句提取，但不代表真实模型的解析能力，也不会在供应商失败时自动接管。

匹配需另外验证两端明确发布、默认不公开、CAS 冲突、编辑/继续对话导致暂停、撤回、角色隔离、对外字段白名单、自然条件的正反样本、硬条件过滤、私密示例不发布且不混入真实结果，以及空状态。真实匹配仅意味着比较真实入库且用户同意展示的记录，不证明发布者陈述属实或已有足够活跃供给。

真实 Qwen 联调需要服务端密钥与匹配地域，使用脱敏或合成样例验证模型遵循提问、纠正和来源规则。`tools/evaluate-discovery.ts` 提供 AI 与企业出海的双向自然段落、确认和纠正验收；真实调用需显式启用。固定合成场景通过不等于全体用户解析准确率或独立专业能力验证；测试替身通过也不能替代真实供应商验收。

账户支持需求方与专业人才两种使用身份；每次流程按当前会话身份选择。发现与匹配按用户和 `kind` 隔离，切换不会覆盖另一身份的草稿、对话或发布。当前身份通过 `/auth/role` 切换；旧页面请求收到 `409 ACTIVE_ROLE_CHANGED` 时刷新会话，不能自动将旧输入提交到新身份。详细合同见 [账户认证](AUTHENTICATION.md#使用身份与会话切换)。
